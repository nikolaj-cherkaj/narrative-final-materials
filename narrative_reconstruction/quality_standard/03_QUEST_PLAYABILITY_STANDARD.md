# 03. Стандарт логической исполнимости заданий

## 1. Цель

Каждый квест должен быть логически исполним по своему тексту и утверждённым правилам игры. Игрок не должен угадывать отсутствующий предмет, способ действия, условие перехода или причину отказа.

Проверяется исполнимость сценария, а не баланс и не фактическая работа движка.

## 2. Карточка стадии квеста

Для каждой значимой стадии установить:

1. Идентификатор/название стадии, если он существует в исходнике.
2. Триггер входа: почему и когда игрок попадает сюда.
3. Участники: кто присутствует и кто действует.
4. Цель: что требуется получить, узнать или сделать.
5. Предпосылки: какие предметы, знания, состояния или предыдущие события необходимы.
6. Источники: откуда берутся необходимые предметы и информация.
7. Действие: кто именно и что делает.
8. Способ: каким уже существующим и понятным способом действие выполняется.
9. Подтверждение: по какому результату ясно, что действие удалось.
10. Изменение состояния: что меняется после действия.
11. Переход: куда ведёт успешный или альтернативный результат.
12. Неуспех: что происходит при отказе, ошибке или невыполненном условии.
13. Повтор: можно ли повторить действие, вернуться или получить ресурс заново.
14. Последствие: что увидит/узнает игрок и какие последующие материалы затронуты.

Не требовать технического описания, если механика уже определена в другом нормативном источнике. Ссылаться на этот источник.

## 3. Трасса прохождения

Для каждого квеста построить пошаговую трассу:

- запуск и доступ;
- получение задачи;
- получение необходимых предметов/информации;
- все обязательные действия;
- все проверки условий;
- все варианты выбора;
- каждый предусмотренный финал;
- отказ;
- провал;
- повторная попытка;
- повторный вход в сцену;
- переход к последующим заданиям.

Для каждого шага ответить: «Что конкретно делает игрок или NPC, на основании какой информации/предмета, и почему это действие доступно именно сейчас?»

Если ответ отсутствует, проверить другие исходники и канон. Только после полного поиска регистрировать дефект.

## 4. Матрица исходов

Минимальная матрица для квеста:

| Путь | Предусловия | Действие | Результат | Состояние/флаг | Дальнейший переход |
|---|---|---|---|---|---|
| Успех | | | | | |
| Альтернативный успех | | | | | |
| Отказ | | | | | |
| Провал | | | | | |
| Повторная попытка | | | | | |
| Повторный вход | | | | | |

Заполнять только реально предусмотренные пути. Не изобретать новые механики, чтобы заполнить пустые клетки.

## 5. Предметы и ресурсы

Для каждого необходимого предмета проверить:
- существует ли он в мире и в соответствующих исходниках;
- где его можно получить;
- кто его выдаёт/продаёт/передаёт;
- когда он становится доступен;
- не требуется ли он раньше, чем его можно получить;
- расходуется ли он;
- можно ли потерять его;
- есть ли предусмотренная повторная выдача;
- одинаков ли предмет в разных пакетах или речь о разных экземплярах.

Различать:
- предмет отсутствует в корпусе;
- предмет существует, но не имеет источника;
- предмет доступен, но условие выдачи неверно;
- предмет был получен, но последующая сцена не учитывает владение;
- предмет одноразовый и не может быть восстановлен;
- предмет передан NPC или утрачен в предыдущем исходе.

## 6. Действия игрока и NPC

Не оставлять обязательные действия на уровне абстрактного результата («освободи», «почини», «договорись», «открой», «собери», «принеси»), если способ выполнения не очевиден из уже известных правил.

Указать:
- действующее лицо;
- объект действия;
- доступный способ;
- необходимый инструмент/предмет;
- условие успеха;
- подтверждение результата.

Если действие выполняет NPC, текст должен устанавливать, что именно делает NPC. Не перекладывать действие на игрока, если исходный сценарий прямо поручает его персонажу.

Не создавать новые QTE, таймеры, проверки, мини-игры, команды или физические механики. Если для решения действительно нужна новая механика, это вопрос владельцу, а не самостоятельное изобретение агента.

## 7. Ветвления и последствия

Для каждого выбора проверить:
- доступны ли все варианты при указанных условиях;
- понятны ли последствия до необратимого выбора, если это требуется логикой сцены;
- сохраняется ли выбранный исход;
- не открываются ли несовместимые ветви одновременно;
- не блокирует ли один путь другой без предупреждения, если игроку нужна такая информация;
- учитываются ли последствия в следующих сценах и пакетах;
- есть ли завершение для каждого предусмотренного пути.

Отказ, провал и альтернативный финал не должны исчезать из анализа. Проверять их отдельно.

## 8. Флаги и состояния

Для каждого состояния проверить:
- точный ID и семантику;
- событие SET;
- все CHECK;
- CLEAR/перезапись или подтверждённое отсутствие сброса;
- достижимость состояния;
- взаимоисключение;
- повторный вход;
- повторную выдачу;
- переходы между пакетами;
- совпадение текста и канонического реестра.

Не считать флаг корректным только потому, что ID встречается в файле. Не придумывать жизненный цикл ради заполнения таблицы.

## 9. Softlock и тупики

Проверять:
- обязательный предмет недоступен;
- NPC исчезает до передачи необходимой информации/предмета;
- ветка требует ранее израсходованный предмет без повторной выдачи;
- условие зависит от события, которое нельзя вызвать;
- отказ закрывает единственный путь без альтернативы;
- провал не имеет восстановления, хотя квест должен продолжаться;
- повторный вход сбрасывает или дублирует состояние;
- два взаимоисключающих состояния могут возникнуть одновременно;
- финал требует знания или действия, которое игроку не предоставили.

Не считать намеренную необратимость ошибкой, если она ясно задана, доступна игроку по правилам и не разрушает необходимую логику.

## 10. Доступность текста

Проверять, что цель, варианты, условия, действия и последствия понятны при последовательном чтении экранным диктором. Не требовать визуального распознавания.

Не тестировать TTS/озвучивание. Не требовать звуковых маяков, тактильных/обонятельных подсказок или новых навигационных систем. Не помечать художественные глаголы зрения как ошибку без доказанной игровой зависимости от зрения.

## 11. Критерий проходимости

Квест проходит проверку, если каждый предусмотренный путь:
- имеет достижимый запуск;
- предоставляет необходимые предметы и информацию;
- содержит понятные действия и условия;
- приводит к определённому результату;
- корректно обновляет состояние;
- не создаёт необъяснимого тупика;
- согласован с последующими сценами и внешними пакетами.

Любой непроверенный путь должен быть явно перечислен. Нельзя писать «квест полностью проходим», если проверен только основной путь.
